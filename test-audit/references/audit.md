# Audit workflow

- Use after [authoring gate](../SKILL.md#authoring-gate).
- Whole-subsystem campaigns: also require [CAMPAIGN.md](../CAMPAIGN.md).

## Junk patterns

Reject new matches unless [retention bar](#retention-bar) identifies independent
contract. Audit existing matches:

- Assertion-free probes, self-comparisons, identity copiers, subject-generated
  expected values.
- Copied inventories/manifests/export lists; exact source/import/string greps.
- Private predicate/call-shape tests duplicating boundary proof; repeated
  invocations/provider-local replays of shared helpers.
- Test-only exports/globals/wrappers; production paths called only by tests.
- Mocks implementing asserted behavior or pretending distinct APIs match.
- Fixtures supplying receipts, admission, callback ordering owner should produce;
  persistence asserted against store path never writes.
- Capability flags asserted instead of promised delivery/acknowledgement.
- Negative controls passing on unrelated guard or unreachable rejection.
- Names promising behavior inputs/assertions never exercise.
- Correction pile-ups: near-identical regression tests added after each small
  fix, with no new failure mode between them.
- Parameter permutations that reach the same branch, equivalence class, and
  result; aggregate (`all`, count, length) or type/None/existence checks
  dominated by a stronger assertion in the same test.
- Call-count or ordering assertions where count/order is mechanics, not
  billing, retry, batching, idempotency, protocol, lock, or cleanup contract.
- Snapshots whose size hides one small behavioral signal.
- Fixture-tautological tests: setup guarantees the asserted state and no
  production code runs.
- Tests reading untracked outputs/one-off run artifacts, or writing to tracked
  files instead of a temp path.
- Skips on an optional dependency the test never imports or calls.
- Coverage-owned tests: threshold mutation, future-only config, or direct
  post-gate helper call that no active production input reaches.
- Dry-run/fake paths that invent success states which a test then asserts.

## Oracle first

Ask where the expected value came from and what failure the test would expose.

- Independent root: specification, known example, external caller, protocol
  fixture, independently derived invariant. Keep.
- Self-referential: same helper, same algorithm under other names, value
  generated by the code under test, mock setup echoed back. Delete, consolidate,
  or find a real oracle.
- A second implementation counts as a cross-check only if it can fail
  differently.

## Dominance

Test A dominates test B only when A protects the same owner, branch, observable
result, and failure domain with an equally independent or stronger oracle.

- A public integration test does not automatically dominate a known numerical
  example, corruption test, or protocol rejection.
- A long snapshot does not dominate a focused test because it asserts more
  fields.
- Without dominance, there is no duplicate: keep both.

## Closed justification loops

Trace test -> production branch -> reason it exists -> independent root.

- A test does not justify production code by exercising it; production code
  does not justify a test by existing. A validator, checksum, receipt, manifest,
  fallback, retry, or self-check that exists only because its test expects it,
  with the test existing only because the machinery was added, is one
  mutual-support cluster.
- Independent roots: current user requirement, real external caller or public
  API, documented protocol/spec, separately controlled key or authority,
  independently supplied digest/manifest, persistence/readback or corruption
  boundary, independent consumer, independently derived numerical result.
- No root reached: delete the whole cluster, production seam and tests
  together. Root reached: keep only the members that serve it.
- A failed search is not proof of a closed loop. Establish the missing purpose
  before deleting.
- Verifier independence check: does the verifier hold knowledge, authority, or a
  failure domain the producer did not generate? Recomputing the same algorithm
  on the same inputs is not verification. Reopening persisted output is, when it
  can catch truncation, partial writes, or schema loss.

## Retention bar

- Keep independent public API, SDK, protocol, config, migration, storage,
  security, platform, default, prompt-byte, generated cross-language, package,
  release, architecture contracts. Keep observable ordering + credible regressions.
- Source inspection valid when cheapest independent guard of user-facing key,
  byte, path, and survives identifier-only refactoring.
- Static/slow ≠ deletion reason. Baseline failure may be product bug:
  reproduce + repair owner; never delete test for it.

## Candidate evidence

- Before editing: read full test, production owner, entry point, callers,
  callees, siblings, overlapping proof, CI routing, history. Dependency-backed
  claims: inspect dependency source/types. Read root/scoped instructions.
- Record each candidate's:
  - Exact name/location + detectable failure.
  - Non-test callers of covered production/support seam.
  - Stronger remaining owner proof, or why none needed.
  - History/reason it exists + deletion it unlocks.
  - Risk + focused validation command.
- Non-trivial suite: build a working evidence map before deleting, one row per
  test or parameter group: current owner, production branch reached, observable
  result, oracle root, failure domain, dominating test if any. Working notes
  only; never commit an audit artifact to prove cleanup. It prevents merging
  tests with different failure semantics, keeping same-branch permutations, and
  deleting production behavior because its only test was redundant.
- Per test, answer: what distinct regression does it protect; would it fail if
  that regressed; is the oracle independent; is stronger coverage present; is
  the boundary public or meaningful; would a harmless refactor break it; was it
  added after a local correction with no new failure mode?
- Missing evidence: no deletion. Discovery read-only; report before edits.
  Prefer few high-confidence candidates. Parallel discovery may split independent
  owners.
- Delete obsolete seams/dead paths; move retained regressions to owner;
  consolidate generic package/dependency contracts.
- Prefer net-negative production LOC. Never add replacement implementation tests
  or turn uncertainty into cleanup.

## Fixtures

- Retiring a fixture and retiring the behavior reached through it are separate
  decisions. Map each fixture-backed test to a current owner first.
- Retire behavior only on evidence it is obsolete or unreachable; move
  surviving behavior to the lowest stable public seam.
- Before removing a cross-layer fixture, confirm one hermetic test still
  crosses current producer, reader, and consumer. Green unit tests at each end
  do not prove that edge.
- Delete the fixture's private builders, fakes, and compatibility fields once
  nothing surviving uses them.

## Adding tests during an audit

Not the default. Add one only when all hold:

- the cleanup removed verification of real external behavior, or exposed a
  concrete protection gap;
- a plausible regression would fail it;
- the expected result has an independent source;
- it observes a meaningful seam, not cleanup details.

Never add a test because a function now lacks a unit test, coverage dropped, or
for symmetry. Prefer adapting a surviving test. A current requirement or
authoritative project doc outranks a historical test asserting obsolete
behavior; an inferred preference does not. Repairing a test that cannot fail
(for example, one that raises before the state it claims to check exists) is
worth added lines.

## Consolidation

- One readable test per distinct behavior, not per branch or helper.
- Parameterize genuine equivalence classes only; no opaque generated matrix.
- Names and failure messages must still localize a real regression.
- Keep low-level tests where the low-level behavior is itself a stable
  contract.
- Never optimize for test count, assertion count, or coverage.

## Validation and handoff

- Proof policy: run owner/sibling tests plus the project's changed-file checks,
  narrowest command that can fail for the intended reason. Never edit the
  checkout during an active test run.
- Removed source greps/plan assertions: exercise owning executable/dry-run.
- Run targeted format and `git diff --check`; find the project's changed-file
  gate (CI config, scripts) and run it for the touched paths.
- Before landing removal batches, run the project's dead-code/unused-file/
  unused-export and dependency checks if it has them: removed tests orphan
  support files and exports that ordinary PR CI can miss.
- Count collected tests before and after, then inspect skips and deselections:
  a smaller total can hide lost execution. Explain any empty collection.
- Check the worktree is unchanged after suites that run compilers,
  materializers, exporters, or code generators.
- Touched a persisted or wire format: check an existing pre-change input
  against the resulting reader, including a rejection the contract requires. A
  round trip through the edited writer and reader can hide a shared regression.
- Inspect `git diff --numstat`; get a final self-review.
- Report causes, removed categories/seams, retained false positives, proof/cost,
  production versus test/support LOC, PR state, follow-ups.
- Commit/push/land only when authorized through native maintainer workflow.
  Refresh from main + rediscover before another audit batch.
